# Spec Delta

## Purpose

将人才评估中已经记录的信息缺失、事实冲突和未获支持的判断转为可追溯的核实清单，为面试官提供中立问题与需要补充的材料，同时把技术执行问题单独呈现，避免让系统故障变成对候选人的负面判断。

## ADDED Requirements

### Requirement: 核实事项必须有明确触发依据

系统 SHALL 仅从已有缺失项、冲突项及被拦截结论生成核实事项，并保留候选人、维度、原因类型和触发记录标识。存在材料引用时 SHALL 保留其原文区间；纯缺失项允许没有原文，但不得虚构引用。

#### Scenario: 缺少项目规模指标
- **WHEN** 项目交付维度已有经历材料，但评估记录明确缺少上线规模和效果指标
- **THEN** 清单包含对应候选人与维度的核实事项，关联缺失记录并请求补充规模或效果依据

#### Scenario: 冲突核实
- **WHEN** 同一项目和时期的材料对是否负责团队管理存在冲突
- **THEN** 清单关联双方引用并请求澄清职责范围，不预先断言其中一方为假

### Requirement: 问题以中立模板生成并限制数量

系统 SHALL 以经过版本管理的中立模板生成面试问题，不添加材料以外的能力断言。每名候选人最多输出八项，按涉及维度权重降序、原因类型及稳定标识排序；相同触发记录不得重复生成，超出部分必须显示剩余数量。

#### Scenario: 信息不足的中立表述
- **WHEN** 记录仅表明无法确认候选人是否主导生产上线
- **THEN** 问题询问其职责、上线范围和可核实材料，不使用“你为什么没有生产经验”等预设性表述

#### Scenario: 重复或过多触发记录
- **WHEN** 同一缺失记录被多个报告位置引用，且候选人存在超过八个不同核实事项
- **THEN** 重复记录合并，显示稳定排序的前八项及剩余数量，相同快照重复读取结果一致

### Requirement: 技术故障独立呈现

系统 SHALL 将解析、取证、评分或审查技术错误显示为技术重试事项，保留失败阶段和可公开原因，不生成暗示候选人能力不足的面试问题。技术错误不得伪装为已经检索但未找到的材料。

#### Scenario: 评分模型超时
- **WHEN** 某维度因模型超时而未评分
- **THEN** 页面提示“评分暂未完成，需要重试”，不询问候选人为何缺少该能力

### Requirement: 清单为只读决策辅助

系统 SHALL 在新报告及历史详情中提供相同的核实事项和来源入口。本期清单为只读，显示问题不会修改材料、评分或生成已完成核实记录；空清单必须说明当前没有待核实事项。

#### Scenario: 查看问题不改变评估
- **WHEN** 用户打开或复制核实问题后刷新报告
- **THEN** 原评分与原材料不变，问题仍为待核实状态，不自动标记为候选人已作答

#### Scenario: 所有信息均被当前材料覆盖
- **WHEN** 没有缺失、冲突、被拦截结论及技术重试事项
- **THEN** 页面说明当前没有待核实事项，不为填充界面生成泛化问题
